# Bootstrap use cases and proofs from an existing repository

Lastro is not always started on an empty repository. Often it starts on a repository with thousands of commits and a lot of code, and before anyone proposes a change, Lastro must know which use cases the application implements today and how it behaves. That baseline must be reviewed by people, like any proposal, so the proofs that guard it are formal and trusted.

`lastro scan` reads the repository without any LLM and prints its size: the tracked files with their role (source, test, doc, config) and exported names, the tests found by name, the manifests, the newest commits with the files they touched, and the areas a large repository can be split into. The same checkout and options always give the same digest and the same hash. `--scope` limits it to some folders, `--max-commits` and `--since` limit the history.

`lastro bootstrap` scans the repository and sends the digest, with source excerpts, to the survey step: the extraction step reading code and commit history instead of prose. The survey proposes the use cases the code implements today, each with its complete current behavior and one behavior per checkable promise. Every behavior must be grounded in files, tests or commits that are in the digest, and the CLI refuses an answer that cites anything else, lists every problem at once, and never lets a bootstrap touch a use case that already has proofs. A use case that is recorded without proofs can have its description corrected.

The answer becomes a bootstrap proposal. Its prose is a generated report with one section per use case and one line per behavior with its grounds, each behavior is an intent with its grounds and a confidence, and the proposal records the commit and the digest it was read from. It may bring the models and subjects its proofs need, which are reviewed with the intents and only join the configuration when the proposal is applied.

A bootstrap proposal is reviewed, derived, proved and applied like any other proposal. The code is the reference: when a bootstrap proof fails, the feedback says not to change the code, because either the reading is wrong and the intent must be amended, or the code has a bug the team must decide about.

In the agent plugin, a bootstrap skill walks the agent through scan, bootstrap, the user's review, derive, prove and apply. When no use case is recorded yet, the gate tells the agent to bootstrap an existing repository first. The review shows each bootstrap intent's grounds and confidence, and the Stop hook never sends a failing bootstrap proof back to the agent as code to fix.
