# B7 — Examples & Dogfood Self-Validation

> Source plan: [`plan.md`](plan.md) §11 (Acceptance Criteria), `CLAUDE.md` rule 7 (dogfood the framework)

The integration verification that the framework actually works: two sample repos exercise the full pipeline, and the framework validates itself.

## Branching (mandatory)

```bash
git fetch origin
git checkout -b feat/b7-examples-dogfood origin/main
```

## Parallelism

- **Can run in parallel with:** nothing — this is the integration close-out.
- **Must run after:** B5 (skills end-to-end) and B6 (CLI end-to-end). All other Phase B chunks must be merged.
- **Blocks:** nothing.

## Scope

In:
- `examples/http-api-sample/` — minimal Go HTTP API with 2–3 endpoints. Canonical detection target. `examples/http-api-sample-broken/` is the deliberately-broken twin for heal-loop acceptance.
- `examples/cli-sample/` — minimal Go CLI repo. Validates archetype branching in `/detect-stack` actually flows downstream.
- Integration test harness that runs the full chain on each sample: `harness detect → harness validate → (if broken) harness heal → harness validate`. Asserts each plan §11 criterion.
- **Dogfood:** `harness detect` against this framework's own repo. The framework's CLI (`cmd/harness`) is the archetype-`cli` subject. Detected use cases must include at least the major skill flows. Generated sensors must execute against the framework's own packages.
- `make verify-self` (or equivalent) target that runs the dogfood pass in CI.

Out:
- Production deployment, packaging, release engineering.
- Additional sample repos beyond the two — later.
- Performance benchmarking — separate concern.

## Open questions for `/brainstorming`

1. **Sample repo scope.** How many endpoints per sample? Recommendation: 2 — one GET, one POST with body validation. Enough fixture variety; cheap to maintain.
2. **Broken-variant location.** Separate `*-broken/` directory or a single repo with `--inject-bug <name>`? Recommendation: separate directory — heal asserts file edits; clean two-tree diff is easier to reason about.
3. **Dogfood failure mode.** If the framework can't detect itself cleanly, does CI fail? Recommendation: yes — CLAUDE.md rule 7 makes self-validation first-class.
4. **Acceptance criteria coverage.** Each of plan §11's 7 criteria → 1 explicit test (`plan_11_criterion_<n>_test.go`).
5. **Fixture reuse demonstration.** Criterion §11.7 requires one fixture used across 2 angles. Asserted at sample-build time (handwritten) or runtime (generated by `/create-sensors`)? Recommendation: runtime — proves the generation logic respects deduplication.
6. **Heal acceptance.** Criterion §11.6 — what's the seed bug? Recommendation: missing status code branch (single-file, unambiguous heal target).

## Deliverable acceptance

Each criterion from plan §11 maps to a passing test:

1. `/detect-stack` covers ≥95% of declared deps + emits archetype with rationale.
2. `/detect-use-cases` produces ≥1 valid use case per public entry point, with `given/when/then`, archetype-typed entry point, ≥1 fixture.
3. Template interpolation resolves cleanly across all generated use cases (use `internal/usecase/template.Resolver`).
4. `/create-sensors` produces grounded sensors per applicable obligatory angle.
5. `/validate-use-case` executes the sensor graph and aggregates (consuming `aggregate.Rollup` + `aggregator/usecase`).
6. Broken sample emits a failing signal whose `HealHint` (already synthesized by `aggregate.synthesizeHealHint`) drives a successful heal in 1 iteration.
7. Same fixture is used across ≥2 angles in the same use case.

Plus:
- `make verify-self` (dogfood) passes locally and in CI.
- README in each `examples/<sample>/` directory explains what it demonstrates.
