## Scope

In:
- `examples/http-api-sample/` — a minimal Go HTTP API repo with 2–3 endpoints. Used as the canonical detection target. Includes a deliberately-broken variant in `examples/http-api-sample-broken/` for heal-loop acceptance.
- `examples/cli-sample/` — a minimal Go CLI repo. Validates that the archetype branching in `/detect-stack` actually changes downstream behavior.
- An integration test harness that runs the full chain on each sample: `harness detect → harness validate → (if broken) harness heal → harness validate`. Asserts each acceptance criterion from plan §11.
- **Dogfood:** `harness detect` against the framework repo itself. Use case: the framework's own CLI (`cmd/harness`) is the archetype-`cli` use case. Detected use cases must include at least the major skill flows (run-sensor, validate-use-case). Generated sensors must execute against the framework's own packages.
- A `make verify-self` (or equivalent) target that runs dogfood as part of CI.

Out:
- Production deployment, packaging, release engineering.
- Additional sample repos beyond the two — those can come later.
- Performance benchmarking — separate concern.

## Open questions for `/brainstorming`

1. **Sample repo scope.** How many endpoints per sample is "enough"? Recommendation: 2 endpoints (one trivial GET, one POST with body validation) — covers entry-point detection + fixture variety without exploding the maintenance cost.
2. **Broken-variant location.** Separate `*-broken/` directory or a single repo with a `--inject-bug <name>` flag? Recommendation: separate directory — the heal flow asserts file edits; clean source-of-truth diff is easier with two trees.
3. **Dogfood failure mode.** If the framework can't detect itself cleanly, does CI fail? Recommendation: yes — CLAUDE.md rule 7 makes self-validation first-class. A flaky dogfood run is a framework bug.
4. **Acceptance criteria coverage.** Each of plan §11's 7 criteria → 1 test case. Recommendation: explicit one-to-one mapping in the test file (`plan_11_criterion_<n>_test.go`) so coverage is visible.
5. **Fixture reuse demonstration.** Criterion §11.7 requires one fixture used across 2 angles. Is this asserted at sample-build time (handwritten YAML) or at runtime (generated by `/create-sensors`)? Recommendation: runtime — proves the generation logic respects the deduplication intent.
6. **Heal acceptance.** Criterion §11.6 says "the heal loop produces a fix on the first attempt." What's the seed bug — typo in handler return, missing endpoint, wrong status code? Recommendation: missing status code branch — concrete, single-file edit, unambiguous heal target.

## Deliverable acceptance

Each criterion from plan §11 maps to a passing test:

1. `/detect-stack` covers ≥95% of declared deps + emits archetype with rationale.
2. `/detect-use-cases` produces ≥1 valid use case per public entry point, with `given/when/then`, archetype-typed entry point, ≥1 fixture.
3. Template interpolation resolves cleanly across all generated use cases.
4. `/create-sensors` produces grounded sensors per applicable obligatory angle.
5. `/validate-use-case` executes the sensor graph and aggregates.
6. Broken sample emits a failing signal whose `heal_hint` produces a working fix in 1 heal iteration.
7. Same fixture is used across ≥2 angles in the same use case.

Plus:
- `make verify-self` (dogfood) passes locally and in CI.
- README in each example directory explains what it demonstrates.
